## 核心设计决策

### 1. 绝对路径支持

**问题**：多人在发时，相对路径可能导致脚本在不同环境中失败。

**解决方案**：所有脚本通过 `SCRIPT_DIR` 和 `PROJECT_ROOT` 自动获取项目根目录绝对路径。

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PROJECT_ROOT="$(cd "$SCRIPT_DIR/.." && pwd)"
```

### 2. 启动等待机制

**问题**：后台启动服务后，无法确认服务是否真正启动成功。

**解决方案**：增加 `wait_for_startup()` 函数，检测日志关键字判断启动状态。

- 后端检测：`若依启动成功`
- 前端检测：`ready in` 或 `Local:`
- 超时时间：30 秒
- 失败时自动清理 PID 文件

### 3. 健康检查

**问题**：需要快速确认服务是否正常运行。

**解决方案**：增加 `--health` 选项，通过 HTTP 请求检查服务状态。

```bash
# 后端健康检查
curl -s -o /dev/null -w "%{http_code}" http://localhost:18080/actuator/health

# 前端健康检查
curl -s -o /dev/null -w "%{http_code}" http://localhost:3888/
```

### 4. 端口占用自动处理

**问题**：端口被占用时需要手动处理，影响开发效率。

**解决方案**：脚本自动检测并终止占用端口的进程，无需用户交互。

```bash
port_pid=$(lsof -ti:$SERVER_PORT 2>/dev/null)
if [ -n "$port_pid" ]; then
    kill -9 $port_pid 2>/dev/null
fi
```

### 5. 日志记录

**问题**：服务运行日志需要便于查看和排查问题。

**解决方案**：
- 所有脚本输出同时发送到屏幕和日志文件
- 日志文件按日期命名和轮转
- 使用 `tee -a` 命令实现双重输出

### 6. 代码生成自动解压

**问题**：生成 ZIP 后需要手动解压查看。

**解决方案**：生成完成后自动解压到同级目录，并显示代码结构。

## 最佳实践提炼

### 1. 脚本设计原则

- **单一职责**：每个脚本只做好一件事
- **用户友好**：提供 `--help` 和清晰的错误提示
- **安全默认**：默认行为安全可靠（如 `--dry-run` 预览）
- **灵活扩展**：支持多种选项组合使用

### 2. 错误处理

- 检查必填参数
- 检查文件/目录是否存在
- 检查依赖工具是否安装
- 提供清晰的错误信息和解决建议

### 3. 日志输出

- 使用分隔线和标题增强可读性
- 关键步骤有明确提示
- 完成后提供下一步操作建议
- 错误时提供常见原因和解决方法

### 4. 文档编写

- 提供快速索引表格
- 每个选项都有说明和示例
- 包含常见问题解答 (FAQ)
- 文档与代码同步更新

## 遇到的问题

### 问题 1：`local` 关键字误用

**现象**：`clean.sh` 在主流程中使用 `local` 导致错误。

**原因**：`local` 只能在函数内部使用。

**解决**：移除主流程中的 `local` 关键字。

### 问题 2：日志目录不存在

**现象**：首次运行时日志文件写入失败。

**解决**：脚本开始时创建日志目录 `mkdir -p "$LOG_DIR"`。

### 问题 3：pnpm 未安装

**现象**：前端脚本无法运行。

**解决**：增加 `check_pnpm()` 函数，自动检测并提示安装。

## 结果与反思

### 成果

- 6 个脚本，总计约 1200 行代码
- 1 个详细文档（487 行）
- 完整的开发流程覆盖

### 反思

1. **启动等待时间**：30 秒对某些环境可能不够，可考虑增加为可配置参数。
2. **健康检查依赖**：需要 `curl` 或 `wget`，在某些环境可能缺失。
3. **测试脚本使用率低**：项目当前没有测试用例，`test.sh` 暂时用不到。
